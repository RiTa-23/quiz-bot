# 技術選定

[要件定義.md](./要件定義.md) / [アーキテクチャ.md](./アーキテクチャ.md) を実現するための技術選定。各項目について選定理由と比較検討を記載する。

---

## 1. 全体構成

| 項目 | 選定 |
|---|---|
| Bot | Discord Hono |
| Web API | Hono |
| Web フロントエンド | React |
| デプロイ先 | Cloudflare Workers |
| DB | Cloudflare D1 |

（詳細構成は [アーキテクチャ.md](./アーキテクチャ.md) 参照）

---

## 2. モノレポ管理

### 選定: bun workspaces

| 観点 | bun (workspaces) | pnpm workspaces | npm workspaces |
|---|---|---|---|
| インストール速度 | 非常に速い | 速い | 遅め |
| Cloudflare Workers/wranglerとの実績 | 実績は増えているが `vitest-pool-workers` 等一部ツールとの相性報告がまだ散見される。問題が出た場合は個別に調査が必要 | Cloudflare公式サンプル・ドキュメントでの採用例が最多 | 標準機能のみで安定 |
| モノレポ機能 | シンプルなworkspace機能。タスク依存管理・キャッシュは弱い | 成熟したworkspace機能 | 基本機能のみ |
| 開発者の習熟度 | 使い慣れている | - | - |

- 開発者がbunに習熟していることを優先し、**bun workspaces** を採用する
- `wrangler` / `vitest-pool-workers` 等のCloudflare系ツールチェーンとの相性でトラブルが出た場合の対応方針:
  - パッケージインストールは `bun install` を使いつつ、`wrangler dev` / `wrangler deploy` の実行自体はNode.js経由（bunはpackage managerとして使うのみ）にすることで影響範囲を限定する
  - `vitest-pool-workers` が bun 環境で不安定な場合は、テスト実行のみ `npx vitest` （Node経由）にフォールバックする選択肢を残す
- 現時点のパッケージ数は `apps/bot` `apps/api` `apps/web` `packages/core` の4つ程度で、Turborepo等のタスクキャッシュが必要になる規模ではない。パッケージ数増加やビルド時間が問題になった段階で導入を検討する

---

## 3. DBアクセス層

### 選定: Drizzle ORM

| 観点 | Drizzle ORM | Kysely | 生SQL（prepared statement） |
|---|---|---|---|
| D1公式サポート | ◎（`drizzle-orm/d1` あり） | △（コミュニティ経由で可能） | ◎（wranglerのAPIそのまま） |
| 型安全性 | 高い（スキーマから型自動生成） | 高い | 低い（手動で型を書く必要） |
| マイグレーション機能 | `drizzle-kit` で管理、`wrangler d1 migrations` と併用可 | 別途ツールが必要 | `wrangler d1 migrations` を直接利用 |
| 学習コスト | 中 | 中 | 低 |

- `packages/core/db` にDrizzleのスキーマ定義（[DB設計.md](./DB設計.md) の各テーブルに対応）を置き、マイグレーションは `drizzle-kit` で生成したSQLを `wrangler d1 migrations` で適用する運用にする

---

## 4. Web フロントエンド

### 選定: Tailwind CSS + shadcn/ui

| 観点 | Tailwind + shadcn/ui | Tailwindのみ | Chakra UI / MUI |
|---|---|---|---|
| 実装速度 | 速い（既製コンポーネントをコピーして調整） | 初期実装コストが高め | 速い |
| カスタマイズ性 | 高い（コンポーネントのコードを直接所有する） | 最も高い（全て自前） | ライブラリの制約に縛られやすい |
| バンドルサイズ | 必要な分だけ | 必要な分だけ | ライブラリ全体分のオーバーヘッドあり |

- shadcn/ui はコンポーネントを `node_modules` ではなくプロジェクト内にコピーする方式のため、Cloudflare Pages/Workers 環境でのビルド互換性の懸念が少ない

---

## 5. バリデーション

### 選定: Zod

- API入力値のバリデーション（Honoのハンドラ内）と `packages/core` の関数の入力型チェックを共通化するために使用
- Drizzleのスキーマから `drizzle-zod` で対応するZodスキーマを自動生成し、DB定義とバリデーション定義の重複を避ける

---

## 6. 認証

### 選定: Discord OAuth2 + Cookieベースセッション

- Web側は Discord OAuth2 でログインし、セッションIDをHTTP Only Cookieに保存
- セッション情報自体はD1の `sessions` テーブル、またはCloudflare Workers KVに保持（KVの方がTTL管理が容易なため推奨）
- Bot側（`apps/bot`）はDiscordのInteractionリクエスト署名検証（`discord-interactions` パッケージ等）で認証し、OAuth2フローとは独立させる（[アーキテクチャ.md](./アーキテクチャ.md) の認証節を参照）

---

## 7. テスト

### 選定: Vitest + `@cloudflare/vitest-pool-workers`

| 観点 | Vitest + vitest-pool-workers | Vitestのみ（coreパッケージ限定） |
|---|---|---|
| カバー範囲 | `packages/core` に加え `apps/bot` `apps/api` のWorker特有の挙動（D1バインディング、Fetch APIなど）も実環境相当でテスト可能 | ビジネスロジックのユニットテストのみ |
| セットアップコスト | 中（`wrangler.toml` のテスト用設定が必要） | 低 |

- `packages/core` はDBアクセスを含むためD1バインディングのモック/実体が必要になり、`vitest-pool-workers` を使うことで実際のD1（ローカルSQLite）に近い環境でテストできる
- 段階的に、まず `packages/core` のロジックテストから着手し、Bot/APIの結合テスト（Interaction処理、HTTPハンドラ）は実装が進んだ段階で追加する

---

## 8. Lint / Format

### 選定: Biome

- ESLint + Prettierの組み合わせと比較して単一ツールで高速に完結し、Cloudflare Workers系のTypeScriptプロジェクトでの採用例も増えている
- モノレポ全体で1つの設定ファイルを共有する

---

## 8-1. 出題セッションの状態管理

### 選定: Cloudflare Durable Objects（SQLiteバックエンド）

複数問セッションと「みんなで早押し」の進行状態・早押し判定に使用する。配置と役割の詳細は [アーキテクチャ.md](./アーキテクチャ.md) の「出題セッションの状態管理」を参照。

| 観点 | Durable Objects | D1にセッションテーブル追加 |
|---|---|---|
| 早押しの同時押し制御 | ◎（単一インスタンスがリクエストを直列処理、原子的に「最初の正解者」を確定） | △（トランザクション/条件付きUPDATEで近似が必要） |
| 進行状態の保持 | ◎（インスタンス単位で状態を保持） | ○（テーブルで管理可能だが行の生存管理が必要） |
| 導入コスト | 中（新クラス・migration設定） | 低（既存D1に追加するだけ） |

- 早押しの正確性（同時押しでも1人だけを勝者にする）を重視し **Durable Objects** を採用
- **WebSocketは使わない**。Discord Botの回答はすべてHTTP Interactionで届くため、Bot⇔Discord間に持続接続は不要。リアルタイム性はDOの排他制御で担保する
- **無料枠**: SQLiteバックエンドのDOは Workers Free プランで利用可能（100,000リクエスト/日、13,000 GB秒/日、ストレージ5GB）。本Botの利用規模なら無料枠で十分。Web側でライブ観戦画面を作るなど将来WebSocketが必要になった場合も、WebSocket Hibernation APIでアイドル時のDuration課金を抑えられる
- 参考: [Durable Objects Pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)

---

## 9. CI/CD

### 選定: GitHub Actions

- PR時: Biomeによるlint、TypeScriptの型チェック、Vitestのテスト実行
- main ブランチへのマージ時: `wrangler deploy` による各Workerへの自動デプロイ（`apps/bot` / `apps/api`）、Cloudflare Pagesへの `apps/web` デプロイ
- D1マイグレーションはデプロイ前のステップで `wrangler d1 migrations apply` を実行

## 6-1. セッションストア（決定）

Cloudflare Workers KV を採用。`apps/api` に `SESSIONS` バインディングとして持たせ、Discord OAuth2ログイン後に発行したセッションIDをキーに `{ userId, username }` をTTL付き（30日）で保存する（`apps/api/src/auth.ts`）。D1ではなくKVを選んだ理由は6節に記載の通りTTL管理の容易さ。

## 8-2. 出題GUI・早押しの仕様（決定）

- **クイズ選択プルダウンの25選択肢超え**: ページングで対応する。1ページ25件をプルダウンに表示し、別途「◀ 前へ」「次へ ▶」ボタンでページを送る。詳細は [要件定義.md](./要件定義.md) 2.2.1
- **早押しの1問あたり制限時間**: 1分。誰も正解しなければDOの `setAlarm` で締め切り次の問題へ進む
- **早押しの参加者募集の期限**: 10分。参加者が集まらないまま経過したら同じく `setAlarm` で募集を打ち切り、セッションを畳んでチャンネルを解放する
- **早押しスコアの記録**: 1人モード（`quiz_attempts`）とは別テーブル `buzz_attempts` に記録し、統計も分けて集計する（[DB設計.md](./DB設計.md)）
